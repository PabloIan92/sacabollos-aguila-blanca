# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Surfaces covered by this contract:** login screen, invite-user screen, responsive app shell (sidebar ↔ bottom tab bar), and the 3 per-role home screens (Dueño, Recepción, Taller) — shipped as empty-state placeholders this phase; real case/turno data lands in Phase 2+.

**Visual language source of truth:** `docs/index.html` (client-approved clickable demo). Palette, type families, and the "ficha de taller con sello de estado rotado" motif are LOCKED per CONTEXT.md D-09/D-10 and are reused exactly, not redesigned. This spec translates that mock into a prescriptive contract for the real React+Vite build, and resolves the few gaps the mock leaves open (real login form instead of role-picker, sidebar chrome, invite screen, empty states).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, inline chip padding |
| sm | 8px | Compact spacing (form field internal padding, meta-line gaps) |
| md | 16px | Default element spacing (card padding, form field gaps) |
| lg | 24px | Section padding (screen margins, drawer body padding) |
| xl | 32px | Layout gaps (between dashboard head and list, login screen vertical rhythm) |
| 2xl | 48px | Major section breaks (login screen top/bottom breathing room) |
| 3xl | 64px | Page-level spacing (rarely needed at this phase's screen sizes) |

Exceptions:
- **Touch targets on tablet:** minimum 44×44px for any icon-only control (bottom tab bar items, close/dismiss buttons), per WCAG 2.5.5/Apple HIG — this rounds the existing demo's 42px `.close-button` up by 2px. Bottom tab bar items target 56px height for comfortable one-thumb reach on a 10-12" tablet held two-handed (per D-10).
- **Sidebar width (desktop):** fixed 220px, not on the 8-pt content scale but matches RESEARCH.md's recommended structure — treat as a layout constant, not a spacing token.

## Typography

Three type families are locked (Oswald/IBM Plex Sans/IBM Plex Mono per CONTEXT.md D-09) — declaring one universal "2 weights" rule across all three would fight that locked system, so this contract declares **2 core UI weights (Regular 400 / Semibold 600, IBM Plex Sans + IBM Plex Mono)** plus **one explicit display exception (Oswald, fixed at 700, uppercase-only, headings/stamps)** — matching `docs/index.html`'s own Google Fonts import, which never loads Oswald below 600.

| Role | Size | Weight | Line Height | Font |
|------|------|--------|-------------|------|
| Body | 16px | 400 (regular) | 1.5 | IBM Plex Sans |
| Label / Data | 13px | 600 (semibold) | 1.3 | IBM Plex Mono — field labels, case codes, patente, eyebrow/kicker text, role chips |
| Heading | 24px | 700 (display exception) | 1.2 | Oswald, uppercase — section headings ("Casos activos", "Turnos de hoy", drawer titles) |
| Display | 40px | 700 (display exception) | 1.1 | Oswald, uppercase — login hero heading, top-level page H1 |

Notes:
- Buttons and interactive labels use IBM Plex Sans 600 (semibold), never 700/800 — the existing demo uses 600/800 inconsistently across `.ghost-button` (600) and `.tab-button` (800, not an imported weight); standardize to 600 in the real build.
- Do not introduce a 5th size or a 3rd core weight without updating this contract.

## Color

The app is status-driven (each case shows a "sello" reflecting its estado), so color carries meaning beyond decoration. The 60/30/10 split below governs *chrome and surfaces*; the **Status Stamp Palette** further down governs *semantic state* and is reused verbatim from `docs/index.html`'s `stateStyles` map — do not invent new stamp colors.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--steel-100` `#eef1f3` | Page background/canvas behind all screens |
| Secondary (30%) | `--white` `#ffffff` (card/ficha surfaces) + `--navy` `#123a6b` (topbar, sidebar, bottom tab bar chrome) + `--graphite` `#1b1d21` (2px card borders — the signature bordered-"ficha" look) | Cards, panels, nav chrome, borders |
| Accent (10%) | `--blue` `#1c4f8c` | Primary CTA buttons ("Ingresar", "Invitar usuario"), hover border on interactive cards/rows, active/selected nav-item indicator |
| Destructive | `--red` `#c0272d` | Reserved for: destructive/critical actions and their confirmations, critical-state stamps ("reclamo a la compañía", "cancelado"), form validation error text/borders, focus-visible outline ring (kept identical to the existing demo's `:focus-visible { outline: 3px solid var(--red) }`) |

Accent reserved for: primary submit buttons (Login "Ingresar", Invite "Invitar usuario"), hover/active affordance on clickable cards and nav items — never used for body text, never used decoratively on static content.

## Screen Specifications

### 1. Login (`/login`)
- Layout: centered single-column, brand/kicker/heading above a single `Ficha` card containing the form (replaces the demo's 3-way role-picker — production login is real email+password; role comes from the `profiles` row after auth, never chosen by the user).
- Kicker: "Acceso al sistema" (mono, red).
- Heading: "INICIAR SESIÓN" (Display, Oswald 700 uppercase).
- Fields: Email, Contraseña (TextField × 2).
- Primary CTA: **"Ingresar"** → loading label **"Ingresando…"**.
- Error state: see Copywriting Contract.
- No "forgot password" flow in this phase (out of CONTEXT.md scope — not mentioned, do not add).

### 2. Invite user (`/invitar`) — visible only to Dueño and Recepción (D-02)
- Kicker: "Alta de usuario".
- Heading: "INVITAR USUARIO".
- Fields: Nombre completo, Email, Rol (`RoleSelect`).
- Primary CTA: **"Invitar usuario"** → loading label **"Invitando…"**.
- Success: banner (green, not a stamp) showing the generated temporary password with a "Copiar" affordance and the copy: "Usuario creado. Contraseña temporal: `{temp}`. Comunicásela en persona — no se envía por email." (Per RESEARCH.md A5: `admin.createUser`, no email invite for this 3-person in-person team.)
- Error states: see Copywriting Contract.

### 3. App shell / responsive nav
- Breakpoint: **820px** (matches `docs/index.html`'s existing `@media (max-width: 820px)` — do not pick a different number).
- `>820px`: `Topbar` + `Sidebar` (220px, left) + content area.
- `≤820px`: `Topbar` (brand + logout only) + content area + `BottomTabBar` (fixed bottom).
- Nav items (shared array, filtered by role — see RESEARCH.md Pattern 3):
  - Casos — dueno, recepcion, taller
  - Turnos — recepcion
  - Facturación — dueno
  - Invitar — dueno, recepcion

### 4. Role home screens (empty-state placeholders this phase)
- **Dueño** (`/`) → "Casos activos" heading, same list chrome others will see, empty state (see Copywriting). Facturación reachable from nav, not from this screen's body.
- **Recepción** (`/`) → "Turnos de hoy" heading, empty state (see Copywriting), quick-access **"Nuevo caso"** button present per D-07 but disabled with tooltip/caption "Disponible en la próxima entrega" since case creation (CASOS-01) is Phase 2 scope — do not wire it to a broken route.
- **Taller** (`/`) → "Casos activos" heading (filtered to en-reparación/esperando-repuesto once Phase 2 ships), empty state (see Copywriting).

## UI Considerations

Applicable state considerations resolved: 11 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Dueño / Recepción / Taller home (list-collection) | ✅ covered | Each home ships a dedicated `EmptyState` with the heading+body copy defined in Copywriting Contract — no home screen ships blank/undefined in Phase 1. |
| loading | Login form, Invite form (interactive-control) | ✅ covered | Submit buttons swap to their "…ando" loading label and disable during the request; no double-submit possible. |
| loading | App shell (nav) | 🧪 backstop | While `AuthProvider` resolves session + profile, the shell must render a neutral loading state (not a flash of the wrong role's nav) before redirecting/rendering — verified at implementation time via a component test asserting no `Sidebar`/`BottomTabBar` renders before `profile` resolves. |
| error | Login form | ✅ covered | Invalid-credentials copy defined in Copywriting Contract; error renders inline below the form, does not clear the entered email. |
| error | Invite form | ✅ covered | Three distinct error copies defined (unauthorized role, duplicate email, generic/network) — the Edge Function's re-validation (RESEARCH.md Pitfall 2) must map to these, never surface raw Supabase/Postgres error text. |
| error | App shell (profile row missing/fetch fails) | ✅ covered | `FullScreenError` component + copy defined — prevents a broken/partial shell from rendering silently if a `profiles` row is missing for an authenticated user. |
| populated | Dueño / Recepción / Taller home (list-collection) | ⚠ unresolved | Out of scope for Phase 1 by design — real case/turno data and its populated-state layout (row density, sort order) is Phase 2+ (CASOS-04 semáforo, CASOS-05 turnos). Planner should treat "populated home layout" as an explicit Phase 2 assumption, not silently reuse whatever Phase 1 ships. |
| partial | Login form, Invite form | ✅ covered | Submit stays disabled until all required fields are non-empty/valid (email format, role selected); no partial-submit path exists. |
| overflow | Sidebar / BottomTabBar (nav) | ✅ covered | Max 4 nav items this phase, each with a short (≤10 char) fixed label — no truncation needed now; if a future phase adds more items, `BottomTabBar` must gain horizontal `overflow-x: auto` (matching `docs/index.html`'s existing `.tabs { overflow-x: auto }` pattern) rather than shrinking touch targets below 44px. |
| overflow | Topbar brand/user info (static-content) | ✅ covered | Reuses `docs/index.html`'s existing `clamp()`-based brand-title sizing and flex-wrap topbar layout — already handles narrow tablet widths. |
| zero-one-many | Dueño / Recepción / Taller home (list-collection) | ⚠ unresolved | Zero-state is covered (see `empty` row above); one-vs-many layout/copy (singular "1 caso" vs plural "N casos") is Phase 2+ scope once real data exists — do not guess plural rules now. |
| long-text | Invite form fields (form) | 🧪 backstop | Long full names/emails rely on native input scroll (no client-side truncation) — verify at implementation time that the `TextField` component doesn't clip or overflow its `Ficha` container at the field's max practical width. |
| long-text | Error messages (interactive-control/form) | ✅ covered | All error copy is short, pre-written Spanish (Copywriting Contract) — the Edge Function and Auth error handlers must map known error codes to this fixed copy, never render a raw/verbose backend error string. |
| media | (none this phase) | — | Photo/media upload is FICHAS-01 (Phase 2) — no media element exists in this phase's surfaces, category not applicable. |
